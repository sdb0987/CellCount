# 염색 세포 검출 AI 모델 분석 및 설계

대상: `C:\project\CellCount\Cell images` (고농도 345장, 저농도 345장, 3088×2076 JPEG)

## 1. 결론

**YOLO26 Object Detection (yolo26s, 입력 1280×864, 단일 클래스 `cell`)** 을 사용한다.
Segmentation 은 지금 단계에서는 쓰지 않는다.

| 항목 | 선택 | 이유 |
|---|---|---|
| 과제 유형 | Object Detection | 필요한 결과가 "개수"이므로 박스면 충분하다 |
| 모델 | YOLO26s | n 보다 작은/옅은 세포 재현율이 좋고, CPU 에서도 장당 약 0.3초 |
| 입력 크기 | 1280×864 | 원본 비율 유지. 세포가 약 25~60px 로 보여 옅은 세포 윤곽이 남는다 |
| 최대 검출 수 | 1000 | YOLO26 기본값 300 은 이미지당 세포 수(140~570)보다 작다 |
| 클래스 | `cell` 1개 | 참조 CSV 가 이미지당 숫자 하나만 요구한다 |

## 2. 이미지 분석

- 파파니콜로 계열 염색으로 보이는 편평상피세포. 분홍(호산성), 녹청(호염기성), 거의 투명한 옅은 세포가 섞여 있다.
- 이미지당 세포 수가 많다(의사 라벨 기준 고농도 평균 447개, 저농도 평균 283개).
- 세포끼리 겹치고 접힌 것이 많다. 반투명이라 겹친 부분의 경계가 불분명하다.
- 짙은 남색 덩어리와 작은 점 형태의 이물질이 있고, 세지 않아야 한다.
- 파일명 규칙 `Lot 위치 샘플.jpg` (위치: 3시, 6시, 9시, 12시, 중앙).

## 3. Detection 과 Segmentation 비교

| | Object Detection | Segmentation |
|---|---|---|
| 개수 산정 | 가능 | 가능 (결과 동일) |
| 라벨 작업 | 세포당 박스 1개 | 세포당 윤곽 다각형. 작업량 5~10배 |
| 겹친 반투명 세포 | 박스가 겹쳐도 각각 검출 | 겹친 영역을 어느 세포에 줄지 모호해 라벨 일관성이 떨어진다 |
| 추론 후처리 | 박스만 | 마스크 복원이 추가되어 느리고 C# 구현이 복잡하다 |
| 추가로 얻는 것 | 없음 | 세포 면적, 세포별 염색 농도·색 |

개수만 필요하면 Detection 이 라벨 비용과 안정성에서 유리하다.
**세포 면적이나 세포별 염색 농도까지 수치화해야 할 때** Segmentation 으로 전환한다. 그때는 이번 Detection 박스를 SAM 계열 모델의 프롬프트로 넣어 마스크 초안을 만들고 사람이 고치는 순서가 효율적이다.

## 4. YOLO26 을 쓰는 이유와 주의점

- NMS 가 필요 없는 end-to-end 구조라 출력이 `[1, N, 6] = (x1, y1, x2, y2, score, class)` 로 단순하다. C# 후처리가 짧아진다.
- 작은 객체용 손실(ProgLoss, STAL)이 들어가 밀집한 작은 세포에 유리하다.
- **주의 1 — 최대 검출 수**: 기본 300개. 학습(`max_det=1000`)과 ONNX 내보내기(`max_det=1000`) 양쪽에서 늘려야 한다.
- **주의 2 — 중복 박스**: NMS 가 없어서 겹친 세포에서 같은 세포를 두 번 잡는 경우가 있을 수 있다. 프로그램에 "중복 제거 IoU"(기본 0.70) 를 두어 거의 같은 박스만 제거한다.

## 5. 학습 데이터 (의사 라벨)

사람이 만든 정답 라벨이 없어서, 참조 프로젝트에 들어 있는 기존 세포 검출 모델로 초기 라벨을 만들었다 (`Training\01_make_pseudo_labels.py`).

1. 기존 ONNX 모델 4종(v8n, v10n, v10s, v10m) × (원본, 좌우반전, 상하반전) = 12회 추론
2. IoU 0.55 이상인 박스를 한 세포로 묶고, 2개 이상 모델이 동의한 것만 채택 (좌표는 점수 가중 평균)
3. 짙은 남색 픽셀이 30% 를 넘는 박스(이물질)와 92% 이상 포함되는 중복 박스 제거
4. 분할: train 570장 / val 120장. 같은 샘플이 양쪽에 섞이지 않도록 Lot·샘플 단위로 나눔 (val = 레브로 전체, EZC 9번 샘플, 2603 의 05 샘플)

기존 모델은 이미지를 640px 로 줄여 추론하고 v10 계열은 300개까지만 검출하므로, 여러 모델을 합쳐 누락을 보완했다.

**한계**: 이 라벨은 사람이 검수한 정답이 아니다. 아래 성능 수치는 "의사 라벨과 얼마나 일치하는가"이지 실제 정확도가 아니다.

## 6. 학습 결과

학습 설정: yolo26s.pt 전이학습, 40 epoch, 배치 4, imgsz 1280, 단일 클래스, RTX 4090 에서 약 2시간 15분.
(배치 8 은 다른 프로그램이 GPU 메모리를 쓰는 상태에서 메모리 부족으로 실패해 4 로 낮췄다.)

### 6.1 검증셋 지표 (120장, 의사 라벨 39,433개 기준)

| Precision | Recall | mAP50 | mAP50-95 |
|---|---|---|---|
| 0.965 | 0.964 | 0.991 | 0.929 |

### 6.2 Threshold 별 세포 수 오차 (검출 수 − 의사 라벨 수, 이미지당 평균 라벨 328.6개)

| Threshold | 평균 검출 수 | 편차 | 평균 절대 오차 | 오차율 | 상관계수 |
|---|---|---|---|---|---|
| 0.10 | 376.6 | +47.9 | 47.9 | 13.9% | 0.997 |
| 0.20 | 355.7 | +27.1 | 27.1 | 7.8% | 0.998 |
| 0.25 | 348.8 | +20.2 | 20.2 | 5.9% | 0.998 |
| 0.30 | 342.8 | +14.2 | 14.3 | 4.1% | 0.998 |
| **0.35** | 337.5 | +8.9 | 9.3 | 2.7% | 0.999 |
| 0.40 | 332.2 | +3.6 | 5.5 | 1.7% | 0.999 |
| 0.50 | 322.1 | −6.5 | 7.4 | 2.2% | 0.998 |

(Python 평가, 중복 제거 없음. `Training\04_evaluate_counts.py`)

**기본 Threshold = 0.35** 로 정했다.

- 점수 구간별로 박스를 그려 눈으로 확인했다. 0.40 이상은 거의 모두 세포였다. 0.25~0.40 구간은 의사 라벨이 놓친 옅은 세포와, 세포 조각·기포·중복이 섞여 있었다. 0.25 미만은 대부분 겹친 세포 위의 중복 박스였다.
- 의사 라벨과 가장 잘 맞는 값은 0.40 이지만, 의사 라벨 자체가 옅은 세포를 일부 놓치므로 한 단계 낮은 0.35 를 택했다. 0.35 와 0.40 의 차이는 이미지당 약 5개(1.6%)다.
- 어느 Threshold 에서도 상관계수가 0.997 이상이다. 즉 Threshold 는 전체 개수를 일정 비율로 올리거나 내릴 뿐 샘플 간 순위는 거의 바꾸지 않는다. 시약 간 상대 비교에는 값을 고정해 쓰는 것이 중요하다.

### 6.3 C# 프로그램 검증 (전체 690장, Threshold 0.35, 중복 제거 IoU 0.70)

| | 고농도 (345장) | 저농도 (345장) |
|---|---|---|
| 평균 세포 수 | 456.4 | 288.0 |
| 범위 | 183 ~ 573 | 141 ~ 421 |

- 처리 시간(읽기 포함, 중앙값): CPU 약 0.27초/장, GPU(DirectML) 약 0.11초/장. 690장 전체가 CPU 3분 17초, GPU 1분 23초.
- Python 과의 일치: 학습과 같은 축소 방식으로 넣은 Python 결과와 C# 결과의 차이는 이미지당 평균 2.6개(21장 표본, 최대 7개)였다.
- 원본(3088px)을 OpenCV 선형 보간으로 한 번에 줄여 넣으면 이미지당 약 15개 더 검출된다. 축소 방식에 따라 개수가 약 3% 달라지므로, 다른 도구로 재현할 때는 축소 방식을 맞춰야 한다.
- 중복 제거(IoU 0.70)는 고농도 이미지에서 평균 6.5개(최대 15개)를 제거한다. 제거된 박스가 실제 중복인지 겹친 별개 세포인지는 사람이 검수하지 않았다.

## 7. 프로그램 구조 (C#, WinForms, .NET 10)

```
CellCount.sln
CellCount\
  Program.cs              GUI / --cli 배치 모드
  MainForm.cs             화면 로직
  Yolo\Yolo26.cs          ONNX Runtime 추론 (전처리, 출력 해석, Threshold·중복 제거)
  Yolo\OnnxRuntimeLoader.cs  onnxruntime.dll 을 먼저 불러 보고, 실패하면 빠진 DLL 과 해결 방법 안내
  Core\ImageItem.cs       파일명 해석, 폴더 스캔
  Core\ResultsReport.cs   Results Report.xlsx 생성 (엑셀, 하위 폴더별 시트)
  Controls\ImageViewer.cs 확대/이동 가능한 결과 뷰어
Models\cellcount_yolo26s.onnx
Training\                 의사 라벨 생성, 학습, 내보내기, 평가 스크립트
```

추론 순서: 원본 → 1280×864 letterbox(회색 114 패딩) → RGB 0~1 텐서 → ONNX Runtime → 원본 좌표 복원 → Threshold → 중복 제거 → 개수.

결과 파일은 엑셀 통합 문서(`Results Report.xlsx`)다. 배치는 참조 CSV 와 같고(1행 = 위치, A열 = Lot, B열 = 샘플), 하위 폴더가 여러 개면 폴더마다 시트를 만든다. 저장 경로 확장자를 `.csv` 로 주면 예전 CSV 형식으로 저장한다.

점수 0.05 이상의 후보를 모두 보관하므로 Threshold 를 바꿔도 다시 추론하지 않는다.

배포: 빌드 폴더(`CellCount\bin\Release\net10.0-windows`)를 `runtimes` 폴더까지 통째로 복사한다. 실행 PC 에는 .NET 10 Desktop Runtime(x64)만 있으면 된다.
onnxruntime.dll 은 Visual C++ 런타임(`vcruntime140`, `vcruntime140_1`, `msvcp140`, `msvcp140_1.dll`)이 필요한데 .NET 은 필요 없어서, 이 런타임이 없는 PC 에서는 프로그램은 뜨지만 검출할 때 "The type initializer for 'Microsoft.ML.OnnxRuntime.NativeMethods' threw an exception." 이 났다.
그래서 빌드할 때 빌드 PC 의 런타임 DLL 을 실행 폴더에 함께 복사하고, 그래도 불러오지 못하면 빠진 파일과 해결 방법(vc_redist.x64.exe 설치)을 보여 준다.
`CellCount.exe --cli` 로 실행하면 `runtime:` 줄에 실제로 불러온 DLL 의 버전과 위치가 나온다.

## 8. 정확도를 올리는 순서

1. 프로그램으로 검출한 결과를 20~30장 골라 사람이 검수한다(누락 추가, 이물질·중복 삭제). 이 세트가 처음으로 생기는 "진짜 정답"이다.
2. 검수 세트로 Threshold 를 다시 정하고 실제 오차를 측정한다.
3. 검수한 라벨을 학습 데이터에 넣어 재학습한다 (`02_train.py` → `03_export_onnx.py`).
4. 염색 성능을 색으로 구분해 보고 싶으면 클래스를 `분홍 / 녹청 / 옅음` 으로 나눈다. CSV 형식을 바꿔야 하므로 이번 범위에서는 제외했다.
